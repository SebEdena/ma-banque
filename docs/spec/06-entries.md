# Spec — Entries

Complements [00-business-requirements.md](./00-business-requirements.md) and [technical-architecture.md](../architecture/technical-architecture.md). Blocked by [03-accounts.md](./03-accounts.md) (`account_id`, the minimal `entries` table, the account/entries route) and [04-categories.md](./04-categories.md) (`category_id`, category CRUD reused by the quick-create shortcut) — both are written and implemented, per [dependencies.md](./dependencies.md). This is the layer-2 pinch point: nothing after it (`07-recurring-entries.md`, `08-reconciliation.md`, `09-statistics.md`) can be written meaningfully until it lands.

## Problem Statement

An account has no way to record day-to-day activity. `03-accounts.md` built the account itself and the system entry that seeds its balance, but the `account/:id` route is still the placeholder `<p>Compte — à venir</p>`: no entry list, no way to add, edit, categorize, or delete a transaction, and no way to mark one as reconciled. Every account is permanently stuck at its opening balance.

## Solution

Implement the `Entry` domain entity end to end — creation, inline editing, deletion, category assignment (with a quick-create shortcut), and the debit/credit↔amount sync — and build the account entries screen (business requirements §4.3): a paginated, virtual-scrolled, reverse-orderable list with inline row editing, a date-range filter, and jump-to-date.

**Deliberately narrower than business requirements §4.3's full description**, matching how `03-accounts.md` already scoped reconciliation out of its own spec:

- The **collapsible reconciliation panel** (reconciled balance, editable bank balance, editable statement date, delta, red/green indicator, and the "unreconciled only" filter that panel gates) is entirely `08-reconciliation.md`'s job. This spec adds `reconciled` as a plain per-entry boolean — togglable from each row, stored, returned — with no aggregate calculation, no panel, and no filter built on top of it.
- **Access to the account's recurring-entries configuration** (business requirements §4.3's last bullet) is entirely `07-recurring-entries.md`'s job. This spec doesn't add an entry point for it.
- **Recurring-entry generation** (`recurring_rule_id`, `last_viewed_date` bookkeeping) stays out of scope; the column already exists on `entries` (reserved by `03-accounts.md`) and is simply never populated by this spec.

**Cross-checked against the existing prototype** (`docs/design/design.html`): the entries list is a plain list (not a table) rendered inside the surface below the account header, with a "Nouvelle écriture" button opening the same inline-row editing pattern used for existing rows; "Aucune écriture ne correspond aux filtres actuels." is the empty-state copy for a filtered-to-nothing list; the reconciliation toggle per row is a 19×19px rounded checkbox tinted `--pointage-ok`/`--pointage-bad` (colors owned by `08-reconciliation.md`'s styling, not redefined here — this spec's row checkbox uses the plain checked/unchecked style, since the green/red semantic only makes sense once the panel exists to explain it).

## User Stories

1. As a user, I want to see my account's entries as a list sorted most-recent-first by default, so that I immediately see my latest activity when I open an account.
2. As a user, I want to reverse the list's sort order, so that I can review from the oldest entry forward when I want to.
3. As a user, I want a dedicated row at the top of the list for creating a new entry, so that adding a transaction feels like a natural extension of the register rather than a separate form.
4. As a user, I want to click an existing entry and have it turn into an editable row in place, so that correcting a mistake doesn't interrupt my flow with a modal.
5. As a user, I want each entry to have a label, category, date, debit/credit type, amount, description, and reconciliation checkbox, so that I can capture everything about a transaction that matters to me.
6. As a user, I want typing a negative amount to automatically flip the debit/credit selector to debit (and vice versa for a change of selector), so that I can enter an amount however feels natural without a separate mental sign-flipping step.
7. As a user, I want to assign a category to an entry from the same list of categories managed in Settings, so that my transactions stay classified consistently across the app.
8. As a user, I want to create a new category on the fly from the entry row, without leaving the entries screen, so that I don't have to break my flow to go to Settings just because I need a category that doesn't exist yet.
9. As a user, I want to leave an entry's category unset, so that I'm not forced to categorize a transaction I haven't decided how to classify yet.
10. As a user, I want to delete a normal entry permanently after a simple confirmation, so that I can remove a mistaken entry without ceremony.
11. As a user, I want the system entry (opening balance) visible in the list but not directly editable or deletable from here, so that the register shows a complete picture while opening-balance changes stay funneled through the account settings modal (`03-accounts.md`).
12. As a user, I want to toggle an entry's reconciled checkbox directly from its row, so that I can mark transactions as matched against my bank statement as I go, ahead of `08-reconciliation.md`'s panel putting that data to use.
13. As a user, I want to filter the list to a date range, so that I can focus on a specific period.
14. As a user, I want to jump directly to a specific date in the list, so that I can find an old entry without scrolling through everything in between.
15. As a user, I want the list to load and scroll smoothly even with years of history, so that a heavily-used account never feels sluggish.
16. As a user, I want an entry generated from a recurring rule to behave exactly like any other entry once created — editable, deletable, no link back to the rule visible or enforced here, so that I never have to think about its origin when managing it day to day.
17. As a developer, I want `EntryRepository` extended (not replaced) with the read/write methods this spec needs, so that the narrow trait `03-accounts.md`/`04-categories.md` already depend on keeps working unchanged.
18. As a developer, I want entry business errors (e.g. "not found", "system entry read-only", "invalid amount") as a `thiserror` enum serialized to Angular, so that the UI can show a precise message per failure case.
19. As a developer, I want entry creation/update/deletion wrapped in use cases tested against hand-written in-memory fakes, so that business rules (amount validation, system-entry protection) are verified without a database.
20. As a user, I want the amount typed into the entry row to be validated the same way the opening-balance field already is (rejecting non-numeric or sub-cent input), so that the app behaves consistently wherever I type money in.

## Implementation Decisions

- **Schema**: extend the existing `entries` table (`migrations/0004_create_entries.sql`, from `03-accounts.md`) with the two columns business requirements §3.3 lists that it doesn't yet have — `label TEXT NOT NULL DEFAULT ''` and `description TEXT NOT NULL DEFAULT ''` — via a new `migrations/0006_entries_label_description.sql` (`0005` is already `04-categories.md`'s seed migration). `category_id`, `reconciled`, and `recurring_rule_id` already exist on the table (reserved by `03-accounts.md`); this spec is the first to populate `category_id` and `reconciled` on non-system rows, and continues to leave `recurring_rule_id` untouched. The existing `entries_account_date` index and the `is_system`-scoped unique index are unaffected.
- **Module layout**: `domain::entry` and `infra::entry` stay the modules, but this spec **modifies** `EntryRepository` rather than purely bolting new methods onto an untouched trait — `03-accounts.md` explicitly scoped that trait to "only what the accounts feature needs" and named `06-entries.md` as the spec that would own its next revision. Concretely: `list_by_account` (paginated, filtered, ordered — see below), `find` (single entry by id, for the edit-in-place load), `create`, `update`, `delete`, and `set_reconciled` are added, and the five existing methods (`sum_by_account`, `last_entry_date`, `exists_non_system_on_or_before`, `count_non_system_by_account`, `count_by_category`) keep their signatures and behavior but get **reworked internally** to share query/row-mapping logic with the new general-purpose methods instead of each issuing its own hand-rolled SQL: `sum_by_account` and `last_entry_date` reuse the same row→`Entry` mapping `list_by_account`/`find` use (one mapper, not three near-duplicate `query_map` closures); `count_non_system_by_account` and `count_by_category` stay dedicated `COUNT(*)` queries (a full row fetch just to count would be strictly worse), but are grouped with the other write/read methods under one trait doc comment describing the whole set as this spec's design, not "the narrow accounts-era set plus extensions." The three free functions already in `infra::entry` (`insert_system_entry`, `update_system_entry_date_and_amount`, `delete_by_account`) are untouched — the trait's new methods only ever touch non-system rows (`is_system = 0` in every `WHERE` clause, enforced in the use case layer, not left to callers to remember). New module: `usecases::entry` (`create_entry`, `update_entry`, `delete_entry`, `list_entries`, `set_reconciled`), `commands::entry` exposing each as a Tauri command, mirroring the `Account`/`Category` module shape.
- **Pagination**: `list_entries` takes `account_id`, an optional date-range filter (`from`/`to`, both inclusive `IsoDate`), a sort direction (`asc`/`desc` by `date`, ties broken by `id` for stability), and an offset/limit pair (`page_size` fixed at a sensible constant, e.g. 50 — implementer's call on the exact number, not user-configurable). Returns entries plus a `has_more` flag rather than a total count, since a `COUNT(*)` on every page would double the query cost for a value the UI (CDK Virtual Scroll, which grows its scrollable range as pages arrive) doesn't need up front. The system entry is always included regardless of filters — it's excluded only from `count_non_system_by_account`/deletion-guard style queries, never from the list itself, matching business requirements §3.3 ("shown in the list but read-only").
- **Jump-to-date**: implemented as a `list_entries` variant (or an added parameter) that, given a target date, returns the page containing the first entry at or before that date in the current sort order, so the frontend can scroll the virtual list to the right offset. No separate command; same pagination machinery, different starting offset.
- **Create/update flow**: `EntryInput` (label, category_id: `Option<i64>`, date, debit/credit type, amount as major-unit `f64` exactly as typed, description) is validated in `usecases::entry` — empty label rejected, amount converted via `money::to_cents` (same helper and same rejection rules `03-accounts.md`'s opening-balance field already uses), category existence is **not** re-validated here (the DB foreign key on `category_id` already rejects an unknown id, same as the existing `entries` schema note documents; the use case surfaces that failure as `EntryError::UnknownCategory` by mapping the SQLite constraint error rather than doing a redundant existence check). `create_entry`/`update_entry` both reject `is_system = true` targets outright (`EntryError::SystemEntryReadOnly`) — the only two places a system entry's date/amount can change remain `03-accounts.md`'s account-settings modal and its `update_system_entry_date_and_amount` free function.
- **Delete flow**: `delete_entry` rejects the system entry the same way (`EntryError::SystemEntryReadOnly`); any other entry is deleted unconditionally (no soft-delete, per business requirements §3.3) after the frontend's confirmation dialog is accepted.
- **Reconciliation toggle**: `set_reconciled(id, reconciled: bool)` is its own narrow use case/command rather than folded into `update_entry`, so toggling the checkbox from the row doesn't require re-sending the whole entry payload. Also rejects the system entry.
- **Debit/credit↔amount sync**: pure frontend behavior, no backend involvement — the row's amount input and type selector are two views over one signed value; typing a negative number flips the selector, flipping the selector negates the stored sign, and the value sent to `create_entry`/`update_entry` is the already-signed major-unit number split into `(type, abs(amount))` by the same `SignedCents`-shaped logic `domain::entry` already models server-side (the frontend doesn't reimplement the split — it sends signed `f64` amount plus letting the existing type field mirror the sign, so the two are always consistent by construction rather than kept in sync by two separate pieces of state).
- **Category quick-create**: the entry row's category field is a dropdown/combobox listing all categories (color + icon swatch, name), backed by `CategoriesApi.listCategories()` — no new backend command. A "Nouvelle catégorie" affordance inside that dropdown opens the existing `CategoryModal` component (`src/app/features/settings/categories/category-modal`) reused as-is; on save, the newly created category is selected on the entry row immediately (no manual re-open of the dropdown needed). `CategoryModal` moving to a shared location vs. being imported cross-feature from `entries` is the implementer's call — either is fine, matching the "shared location, implementer's call" precedent from `03`/`04`'s pickers.
- **Frontend**: `EntriesApi` injectable service (`src/app/core/entries-api`, mirroring `AccountsApi`/`CategoriesApi`) wraps `invoke()` for `create_entry`, `update_entry`, `delete_entry`, `list_entries`, `set_reconciled`. `Account` (`account.ts`/`account.html`, currently the placeholder) becomes the entries screen: header showing the account (reusing the color/name/icon presentation established on the home screen's cards), the entries list (Angular CDK Virtual Scroll over pages fetched from `EntriesApi.listEntries`, appending as the user scrolls), the "Nouvelle écriture" creation row pinned at the top, inline row→edit-row toggling on click, the reverse-order control, the date-range filter, and jump-to-date. Amounts and dates render through `DisplaySettingsService`'s existing `currency-format`/`date-format` pipes (`05-settings-remainder.md`) exactly as the home screen already does for account balances — this spec introduces no new formatting logic. Per business requirements §5, the current account's accent color is applied to every interactive element on this screen (buttons, checkboxes, selects, the entry row, filters) — the same styling rule `03-accounts.md`'s account cards partially exercise, now applied screen-wide for the first time.
- **Error display**: `EntryError` variants (`SystemEntryReadOnly`, `UnknownCategory`, invalid amount, not found) surface as toasts per `technical-architecture.md` §2.2; empty-label validation is inline next to the field, not a toast, matching the account/category modals' split between field-level and toast-level errors.

## Testing Decisions

- Use case tests (`create_entry`, `update_entry`, `delete_entry`, `set_reconciled` — each including the system-entry-rejection path — plus `list_entries` covering date-range filtering, both sort directions, and pagination boundaries) against a hand-written in-memory fake `EntryRepository` updated to implement the reworked trait — no `mockall`, per `technical-architecture.md` §1.6.
- Domain unit tests for the amount validation reuse (`money::to_cents` is already covered by `03-accounts.md`'s tests; this spec adds no new conversion logic, only new call sites — no duplicate test coverage needed there).
- SQLite integration tests for the new `SqliteEntryRepository` methods (`list_by_account` pagination/filter/sort, `find`, `create`, `update`, `delete`, `set_reconciled`), against a fresh `:memory:` database with all migrations (through `0006`) applied per test, extending the existing `infra::entry` test module rather than adding a parallel one. Includes a case asserting `create`/`update` against an unknown `category_id` surfaces `EntryError::UnknownCategory` (the foreign-key-driven path), and a case asserting `list_by_account` always includes the system entry regardless of the active date-range filter. The existing tests for `sum_by_account`, `last_entry_date`, `exists_non_system_on_or_before`, `count_non_system_by_account`, and `count_by_category` (written in `03-accounts.md`/`04-categories.md`) must keep passing unchanged — this spec reworks their internals to share query/row-mapping code with the new methods, but their observable behavior is not allowed to change, and no new test coverage is owed for them beyond that regression guarantee.
- Angular component tests (Vitest) for `Account`: renders a page of entries from a mocked `EntriesApi`, the system entry renders read-only (no edit-in-place, no delete affordance), creating an entry via the top row calls `EntriesApi.createEntry` and the list refetches/prepends, clicking an existing row toggles it into edit mode and saving calls `updateEntry`, deleting (behind confirmation) calls `deleteEntry`, the reconciled checkbox calls `setReconciled`, typing a negative amount flips the type selector and vice versa, the date-range filter and reverse-order control change what's requested from `EntriesApi`, the category dropdown's quick-create path opens `CategoryModal` and selects the result on save. Mock `EntriesApi`, not `invoke()` directly, per the seam already established for `03-accounts.md`/`04-categories.md`.
- E2E (WebdriverIO, `e2e/entries.e2e.ts`): open an account from the home screen, create an entry via the inline row, edit it in place, toggle its reconciled checkbox, delete it behind confirmation, and create a category via the entry row's quick-create shortcut and confirm it's selected — asserting on `data-testid` hooks, sharing the WDIO session per `technical-architecture.md` §2.3. This is also the spec that finally exercises `04-categories.md`'s deferred "blocked-with-count" delete scenario (a category referenced by a real entry) — `e2e/categories.e2e.ts` gets that scenario added here, using an entry this spec's test setup creates, per the note left in `04-categories.md`'s own Testing Decisions.

## Out of Scope

- The collapsible reconciliation panel, reconciled/bank balance delta calculation, and the "unreconciled only" filter (§3.5, §4.3) — `08-reconciliation.md`. This spec only adds the plain `reconciled` boolean and its per-row toggle.
- Recurring entries (§3.4): the rule entity, generation-on-open/on-startup behavior, and the entries screen's access point into that configuration — `07-recurring-entries.md`. `recurring_rule_id` stays reserved and unpopulated.
- Statistics' per-category/per-month breakdown (§4.5) — `09-statistics.md`.
- Category hierarchy — already out of scope per `04-categories.md`.
- `last_viewed_date` bookkeeping on the account (business requirements §3.1) — meaningless until `07-recurring-entries.md` gives it a reader.

## Further Notes

- This is the layer-2 pinch point per `dependencies.md`: `07-recurring-entries.md`, `08-reconciliation.md`, and `09-statistics.md` all build directly on the `entries` table shape and the `EntryRepository`/`EntriesApi` surfaces this spec finalizes, so get the pagination/filter contract (`list_entries`'s parameters and return shape especially) reviewed carefully before merging.
- `08-reconciliation.md` will need to read the `reconciled` flag this spec introduces and the `date`/`amount` fields already present — no schema change anticipated on its end, only new aggregate queries.
- `07-recurring-entries.md` will need `EntryRepository::create` (or an equivalent insert path) to write generated occurrences with `recurring_rule_id` set — this spec's `create` method doesn't accept that parameter yet since nothing populates it; `07` extends the method signature (or adds a sibling) rather than this spec speculatively adding an unused parameter now.
