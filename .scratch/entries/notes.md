# Entries — implementation notes

## Cross-issue notes

- `EntriesApi` lives at `src/app/core/entries-api/entries-api.ts`, mirroring `AccountsApi`/`CategoriesApi`. Ticket 02 only added `listEntries`; tickets 03+ extend the same class with `createEntry`/`updateEntry`/`deleteEntry`/`setReconciled`. `parseEntryError` is in the same file and already covers every `EntryError` kind, so the write commands need no new mapping.
- Tauri command arguments are sent camelCase (`{ accountId, query }`) — Tauri v2 renames them to the Rust snake_case parameters.
- The entries screen is `src/app/features/account/account.ts` — the smart container, with two presentational children (`entry-row/`, `entry-form/`). State is signals: `sort`, `from`, `to`, `jumpTarget`, `entries`, `hasMore`, `loading`, plus a `generation` counter that discards pages arriving after the query moved on. Any refetch after a create/update/delete (ticket 03) should reuse that path rather than mutating `entries` in place, or the counter stops meaning anything.
- The entries buffer always starts at offset 0 and grows by appending — CDK Virtual Scroll renders one array, so a page starting further in has nothing to sit behind it. That's why jump-to-date loads forward page by page instead of using `list_entries`' `jump_to_date` parameter, which returns a page without reporting which offset it resolved to. `jump_to_date` is still declared on `ListEntriesQuery` (the wire shape) and always sent as `null`. If a later ticket wants the shortcut, the backend needs to return the resolved offset alongside the page.
- `PAGE_SIZE` is 50, defined in `account.ts`.
- Row markup uses `data-testid="entry-row"` with `data-entry-id` and `data-system` attributes; per-field ids are `entry-date`, `entry-category`, `entry-label`, `entry-amount`, `entry-reconciled` (non-system) / `entry-system-checkbox` + `entry-locked` (system). Controls are `entries-from`, `entries-to`, `entries-sort-toggle`, `entries-reset-filters`, `entries-jump-date`, `entries-jump`, `entries-empty`, `entries-viewport`. The e2e spec (`e2e/entries.e2e.ts`, ticket 05) should build on these.
- Business requirements §5's "accent colour on every interactive element" is implemented once, not per control: the screen's root binds `[style.--account-color]="account.color"` and each interactive element opts in with a bare `data-accent` attribute, which `account.css` keys its `accent-color`/hover/focus rules on. New controls added by later tickets just need `data-accent`.
- Category display on a row is read-only here (swatch + name, `lucideFlag`/"Solde initial" for the system entry, `lucideEllipsis`/"Aucune catégorie" when unset), fed by `CategoriesApi.listCategories()`. Ticket 04's quick-create dropdown replaces that cell in edit mode.
- `InMemoryEntriesApi` (`src/app/core/mocks/entries-api.mock.ts`, wired in `app.config.ts`) seeds 240 entries plus a system entry per account so `npm run start:mock` exercises pagination. Ticket 03 made it mutable: `createEntry`/`updateEntry`/`deleteEntry`/`setReconciled` act on the seed and reject like `usecases::entry` does (`EmptyLabel`, `InvalidAmount`, `SystemEntryReadOnly`, `NotFound`), so the mock UI hits the same toasts as the real backend.
- The creation row and the edit-in-place row are **one** `EntryForm` component (`entry-form/`), instantiated twice from `account.html`: above the viewport when `editing() === 'new'`, and inside `*cdkVirtualFor` in place of the row's `EntryRow` when `editing() === entry.id`. It started as one `<ng-template>` rendered twice through `*ngTemplateOutlet`; the PR #6 review turned it into a component, which keeps "one form, two placements" while making the context typed. `editing` is a single signal (`'new' | number | null`), so only one form is ever open and one `draft` signal (`EntryDraft`: `label`, `description`, `date`, `categoryId`, `amount`) can serve both, two-way bound into the child. Edit that one component, not two markups.
- The smart/dumb split (PR #6 review): `Account` owns every `EntriesApi`/`CategoriesApi` call, the paging buffer, `editing`, the `draft` and the modals; `EntryRow` and `EntryForm` inject nothing and emit intents (`reconciledToggled`, `deleteRequested`, `saved`, `cancelled`, `categoryCreateRequested`). Date/currency formats reach `EntryRow` as inputs rather than through `DisplaySettingsService`, so the children stay provider-free in their specs. `reconciled` is an input on `EntryForm` rather than part of the draft, because on an existing entry the checkbox goes straight to `set_reconciled` instead of through the save button. Parsing the amount text and toasting on rejection stay in the container.
- The row `<div>` that `*cdkVirtualFor` repeats stays in `account.html` — it carries the fixed `ROW_HEIGHT`, the click/Enter edit target and the `data-testid="entry-row"`/`data-editing` attributes. The children are `display: contents` so their fields remain flex items of that row.
- `[data-accent]`'s rules moved from `account.css` to `accent.css`, listed in the `styleUrls` of all three components: view encapsulation scopes styles per component, so a child rendering a `data-accent` control needs the stylesheet itself. `--account-color` still comes down by inheritance from the screen's root.
- The form's category cell is a native `<select>` (`entry-form-category`) with an `Aucun poste` option plus one per category, and a colour/icon swatch beside it driven by the `draftCategory()` computed. Native rather than the prototype's custom dropdown because a floating panel inside the CDK virtual-scroll viewport would be clipped by its `overflow`. Ticket 04's quick-create can be an extra option in that select (e.g. a sentinel value handled in `setCategory`) that opens `CategoryModal`, then sets `draftCategoryId` to the created category — no repositioning work needed.
- Debit/credit is not stored: `draftAmount` holds the amount field's **raw text including its sign**, and `draftIsDebit()` is just `startsWith('-')`. The selector rewrites the sign on that text; typing a sign flips the selector. That's why the field is `type="text" inputmode="decimal"` and not `type="number"` — a number input drops an intermediate lone `-`. `amountValue()` converts to the signed `f64` sent to Rust (comma normalised to dot, nothing-after-the-sign is 0) and returns `null` only for text that isn't a number at all; sub-cent precision is deliberately left for `money::to_cents` to reject as a toast.
- Every write except the reconciled toggle refetches the whole buffer from offset 0 (`reload()` — bumps `generation`, clears `entries`, refetches), because a new or edited entry can land anywhere in the current order. `setReconciled` instead patches the single row in `entries` with the returned entry, so ticking a checkbox mid-list doesn't scroll the list back to the top.
- New testids: `entries-new` (opens the creation row), `entry-new-row`, `entry-form-date`/`-category`/`-label`/`-label-error`/`-description`/`-amount`/`-debit`/`-credit`/`-reconciled`, `entry-save`, `entry-cancel`, `entry-delete`. The delete confirmation reuses `ConfirmDialog`, so its buttons stay `confirm-accept`/`confirm-cancel`. A row being edited carries `data-editing="true"`.
- "Pinned at the top" reads as the prototype builds it: a toolbar button (`entries-new`) opens the creation row above the viewport, rather than an always-present empty row — `docs/design/design.html` gates the same row on `isCreatingEntry`, and spec 06 describes "a 'Nouvelle écriture' button opening the same inline-row editing pattern".
- Amount validation (amended by PR #6's review, spec 06 §Error display updated to match): text the form can't read as a number is **both** an inline error (`entry-form-amount-error`, "Montant invalide", plus a destructive border) and a toast — the reviewer's point being that the inline one names the field. Gated on `submitted()` like the empty-label error, so a fresh creation row (which opens on a lone `-`) isn't red before anyone has tried to save. `money::to_cents`' sub-cent rejection stays a toast only: it's the backend's rule, and re-implementing it in `amountValue()` to render it inline would put the same rule in two places. If that inconsistency ever bites, the fix is for `create_entry`/`update_entry` to say which field they rejected, not to duplicate the rule.
- Quick-create is the last `<option>` of the category select — `value="__new__"` (the `NEW_CATEGORY_VALUE` constant exported from `entry-form.ts`), labelled `+ Nouvelle catégorie…`, testid `entry-form-category-new`. `setCategory` (on `EntryForm`) takes the `<select>` element rather than its value, because the sentinel is a trigger and not a value: it puts the field back on the draft’s `categoryId` before emitting `categoryCreateRequested`, so cancelling doesn't leave it showing a non-category. The options carry `[selected]` per-option rather than a bound `[value]` on the select, which is also what makes the created category select itself once its option renders. E2E (ticket 05) drives it with a native select-by-value on `entry-form-category`, then `CategoryModal`'s own `category-name`/`icon-option`/`category-save`/`category-cancel` testids.
- `CategoryModal` is imported cross-feature (`@features/settings/categories/category-modal/category-modal`) rather than moved to `@shared` — spec 06 leaves that to the implementer, and one importer doesn't justify the move. If a third screen needs it, move it then.
- After a quick-create the screen refetches `listCategories()` instead of appending the created category, so the new option lands in the backend's own `name COLLATE FRENCH_NOCASE` order rather than at the end of the list.
- The accent opt-in has a second flavour: `data-accent-solid` (in `account.css`) for controls that already wear the accent as a background — or own their hover colours, like the destructive delete button. It grants the focus ring but not `[data-accent]`'s hover recolour, which would tint a filled button's label to the colour it sits on (it made the "Nouvelle écriture" label vanish on hover).
- Two WebdriverIO gotchas the e2e specs hit against the Linux WebKit webview, both worked around in `e2e/entries.e2e.ts`: an `option:checked` selector never matches a `<select>` selection Angular made by property binding (assert `toBeSelected()` on the option instead), and an element resolved just before a list refetch reads back as empty text (assert with a selector that re-queries, e.g. an xpath `contains(., …)` plus `toExist`, rather than `toHaveText`).
- E2E locator helpers stay pure locators in `e2e/support/*.ts` (`entryRow`, `categoryOption` joined `accountCard`/`categoryCard`); multi-step flows are spelled out in the spec files themselves, even when two specs perform the same setup.
- Click-to-edit opens the form on the column the pointer was over: the row's `(click)` passes `$event` to `startEdit`, `clickedField` maps the nearest `[data-testid]` ancestor (`entry-date`/`-category`/`-label`/`-amount`) to an `EntryFormField`, and `EntryForm` focuses it from an `afterNextRender` in its constructor — the form is created when editing starts, so its first render is the one moment the field exists and the user hasn't focused anything else yet. Anything else (the description line, the row's padding, the Enter key path, the creation row) falls back to `label`. Reconcile and delete keep their `stopPropagation`, so they never reach this.
- Débit/Crédit and save/cancel are **not** accent-coloured: the sign a button sets is the same semantic the row's amount already carries, so Débit/cancel reuse `destructive` and Crédit/save reuse `emerald-600`/`dark:emerald-500`, matching `entry-row.html`'s `text-destructive` / `text-emerald-600 dark:text-emerald-400`. `accountColor()` stays bound only on the form's reconciled checkbox. Cancel takes the delete button's soft `bg-destructive/10` treatment rather than a solid fill, so the green save stays the primary action of the pair; it moved from `data-accent` to `data-accent-solid` now that it owns its hover colours.
- The row's date column and the form's `<input type="date">` are both `w-[116px]` (were `w-[88px]`): at 88px the native calendar indicator sat on top of the digits. The two must stay equal — the row and the form are the same flex row, so the columns only line up while their widths match.
- The category select stays native and icon-less per option: `<option>` can't host an `<ng-icon>`, and the floating panel a custom dropdown would need is still clipped by the virtual-scroll viewport. The swatch beside it is the icon-in-control affordance, and it already tracks the selection live — `categorySwatch()` reads `draft().categoryId`, which `setCategory` patches on `(change)`.
