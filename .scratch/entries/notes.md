# Entries — implementation notes

## Cross-issue notes

- `EntriesApi` lives at `src/app/core/entries-api/entries-api.ts`, mirroring `AccountsApi`/`CategoriesApi`. Ticket 02 only added `listEntries`; tickets 03+ extend the same class with `createEntry`/`updateEntry`/`deleteEntry`/`setReconciled`. `parseEntryError` is in the same file and already covers every `EntryError` kind, so the write commands need no new mapping.
- Tauri command arguments are sent camelCase (`{ accountId, query }`) — Tauri v2 renames them to the Rust snake_case parameters.
- The entries screen is `src/app/features/account/account.ts` — one component, no sub-components yet. State is signals: `sort`, `from`, `to`, `jumpTarget`, `entries`, `hasMore`, `loading`, plus a `generation` counter that discards pages arriving after the query moved on. Any refetch after a create/update/delete (ticket 03) should reuse that path rather than mutating `entries` in place, or the counter stops meaning anything.
- The entries buffer always starts at offset 0 and grows by appending — CDK Virtual Scroll renders one array, so a page starting further in has nothing to sit behind it. That's why jump-to-date loads forward page by page instead of using `list_entries`' `jump_to_date` parameter, which returns a page without reporting which offset it resolved to. `jump_to_date` is still declared on `ListEntriesQuery` (the wire shape) and always sent as `null`. If a later ticket wants the shortcut, the backend needs to return the resolved offset alongside the page.
- `PAGE_SIZE` is 50, defined in `account.ts`.
- Row markup uses `data-testid="entry-row"` with `data-entry-id` and `data-system` attributes; per-field ids are `entry-date`, `entry-category`, `entry-label`, `entry-amount`, `entry-reconciled` (non-system) / `entry-system-checkbox` + `entry-locked` (system). Controls are `entries-from`, `entries-to`, `entries-sort-toggle`, `entries-reset-filters`, `entries-jump-date`, `entries-jump`, `entries-empty`, `entries-viewport`. The e2e spec (`e2e/entries.e2e.ts`, ticket 05) should build on these.
- Business requirements §5's "accent colour on every interactive element" is implemented once, not per control: the screen's root binds `[style.--account-color]="account.color"` and each interactive element opts in with a bare `data-accent` attribute, which `account.css` keys its `accent-color`/hover/focus rules on. New controls added by later tickets just need `data-accent`.
- Category display on a row is read-only here (swatch + name, `lucideFlag`/"Solde initial" for the system entry, `lucideEllipsis`/"—" when unset), fed by `CategoriesApi.listCategories()`. Ticket 04's quick-create dropdown replaces that cell in edit mode.
- `InMemoryEntriesApi` (`src/app/core/mocks/entries-api.mock.ts`, wired in `app.config.ts`) seeds 240 entries plus a system entry per account so `npm run start:mock` exercises pagination. Ticket 03 needs to make it mutable (it currently only reads).
