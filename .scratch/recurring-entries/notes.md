# Recurring entries — cross-issue notes

## Cross-issue notes

_From issue 01 (recurring-rule-backend):_

- **The occurrence write lives on `RecurringRuleRepository`, not `EntryRepository`.** The spec's "`EntryDetails` gaining `recurring_rule_id`" was not done; `EntryDetails` is untouched and no existing call site changed. Instead `RecurringRuleRepository::insert_occurrence_if_absent(rule_id, account_id, date, template) -> Result<bool, RecurringError>` writes the entry directly, because the write is insert-if-absent against the partial unique index and that is a recurring-rule concern. **Issue 02's generator should call this, not `EntryRepository::create`.** `Ok(false)` means "already generated"; the return value is what a generated-count should be summed from.
- **The insert swallows exactly one conflict.** `is_duplicate_occurrence` matches a UNIQUE violation naming `entries.recurring_rule_id` + `entries.date`; every other failure surfaces as a `RecurringError`. Do not "simplify" this back to `INSERT OR IGNORE` — that would report a genuine write failure as "already generated" and silently drop an entry the user is owed.
- **Repository methods already built for generation, currently unused** and carrying `#[allow(dead_code)]` on the trait: `list_overrides`, `delete_override`, `insert_occurrence_if_absent`. Also `domain::recurring::occurrences_between` and `infra::clock::today()`. **Issue 02 should delete those three `#[allow(dead_code)]` attributes** (on the trait in `domain/recurring.rs`, on `occurrences_between`, and on `clock::today`) once it wires them up.
- **Override consumption is not implemented** — only its storage is. Issue 02 owns: applying an override's template to its occurrence, deleting it in the same transaction, and pruning overrides whose `occurrence_date` has passed unconsumed.
- **`last_viewed_date` is still never written.** Issue 01 touched no account code; the window bookkeeping is entirely issue 02's.
- **Naming on the wire** (issue 03's `RecurringRulesApi` must match): commands are `list_recurring_rules` / `create_recurring_rule` / `update_recurring_rule` / `delete_recurring_rule`. The rule payload is _flat_ — `{ label, category_id, amount, description, frequency, interval, start_date, end_date }` — not split into template/schedule objects the way the Rust domain is. `amount` is a signed major-unit number (negative = débit), dates are `YYYY-MM-DD` strings, `end_date` is nullable.
- **`frequency` and `scope` cross the wire as raw strings**, parsed in Rust so a bad value returns a `RecurringError` rather than a deserialization failure. Accepted values: `WEEKLY` / `MONTHLY` / `YEARLY`, and `ALL_FUTURE` / `NEXT_OCCURRENCE_ONLY`. `update_recurring_rule` takes `scope` as a third argument alongside `id` and `input`.
- **The backend decides when scope matters, so the UI's dialog is advisory.** `update_rule` compares the submitted schedule against the stored one; if it differs, the edit is forced to `AllFuture` and the rule's outstanding overrides are discarded, _whatever_ scope was passed. Issue 03 still needs to skip the dialog for schedule-only edits (user story 21), but sending the "wrong" scope cannot corrupt anything.
- **`RecurringError` kinds issue 03's `parseRecurringError` must cover:** `NotFound`, `EmptyLabel`, `InvalidInterval`, `EndDateBeforeStartDate`, `UnknownCategory`, `InvalidAmount`, `InvalidStoredValue`, `Io`. Serialized as `{ kind, message }` like `EntryError`.
- **Known non-atomicity, deliberately left:** a schedule change does `update` then `delete_overrides` as two repository calls with no transaction (the two-repositories-one-connection constraint means a use case can't hold one). A crash between them leaves a stale override, which issue 02's "prune overrides whose date has passed" makes self-healing.
- **`IsoDate` gained `add_weeks` / `add_months` / `add_years`**, all infallible and clamping day-of-month via the existing `days_in_month`. `chrono` was added but is used _only_ by `infra::clock::today()`; date arithmetic is deliberately hand-rolled on `IsoDate` so `domain` stays dependency-free. Don't reach for `chrono` elsewhere.

_From issue 02 (generation-engine-and-startup-wiring):_

- **`RecurringRulesApi` now exists at `src/app/data/recurring-rules/`** with `openAccount(accountId): Promise<number>` and `generateAllDue(): Promise<void>`, plus `parseRecurringError` covering all eight kinds and an `InMemoryRecurringRulesApi` wired into `app.config.ts`'s `mockProviders`. **Issue 03 extends this file rather than creating one** — add the four CRUD methods to the same injectable, the mock, and the mock provider. `parseRecurringError` is already written; don't duplicate it.
- **The generated-count toast is pluralized**, via an exported `generatedEntriesMessage(count)` in the same file: `1 écriture générée` / `N écritures générées`. Issue 04's e2e should match on that wording, not on the spec's illustrative "N écritures générées".
- **Wire names for generation: `open_account` and `generate_all_due_entries`.** `open_account` takes `accountId` and returns the count; `generate_all_due_entries` takes nothing and returns nothing.
- **An archived account generates nothing _and is not stamped_, on both paths** — not just in the sweep. The spec assumed archived accounts have no open path, but the home screen routes to every card it shows, archived list included, so the guard lives in `generate_due_for_account` itself. Leaving the stamp stale is deliberate: unarchiving backfills the period the account spent archived. **Issue 04 should not expect an archived account's register to grow when opened.**
- **`Account` generates once per account id, not once per load.** The screen keeps a `Map<accountId, Promise>`, so the filter/sort/date controls — which re-run its load effect — don't re-call `open_account`. A generation failure resolves that promise rather than rejecting, so the register always loads.
- **Component tests of `Account` now need three rounds of `fixture.whenStable()`** before `detectChanges`, because a load is `openAccount` → `listEntries` → signal write deep. `account.spec.ts`'s `settle()` already does this; anything new driving that screen should use it. Both `Account` and `App` specs `vi.spyOn(toast, …)` rather than `vi.mock`ing `@spartan-ng/brain/sonner` — mocking the module breaks the dialogs and the toaster host built on the rest of it.
- **`AccountRepository` gained `set_last_viewed_date(id, date)`.** `last_viewed_date` means "the date through which this account's recurring occurrences have been generated" and nothing else; no other code should write it.
- **`generate_due_for_all` stops at the first failing account** (propagates with `?`), leaving later accounts ungenerated. Not a spec requirement either way — if issue 03 or 04 wants a partial sweep to keep going, that's the line to change.

_From issue 03 (recurring-rules-ui):_

- **The `data-testid` vocabulary issue 04 should drive.** Toolbar: `recurring-open`. Modal root: `recurring-modal`; create affordance `recurring-new`; empty state `recurring-empty`. List rows: `recurring-row` (each carries `data-rule-id`), with `recurring-row-category` / `recurring-row-label` / `recurring-row-schedule` / `recurring-row-amount` inside, and `recurring-edit` / `recurring-delete` per row. Form: `recurring-form` wrapping `recurring-form-label`, `-category`, `-swatch`, `-debit`, `-credit`, `-amount`, `-description`, `-frequency`, `-interval`, `-start-date`, `-end-date`, `-end-date-clear`, plus `recurring-save` / `recurring-cancel` and the four `recurring-form-<field>-error` nodes. Scope dialog: `recurring-scope-dialog` with `recurring-scope-next` / `recurring-scope-all` / `recurring-scope-cancel`.
- **Deletion reuses `ConfirmDialog`, so its buttons are the shared `confirm-accept` / `confirm-cancel`** — there is no `recurring-`prefixed confirm button. Same for dismissing the modal: it is `ModalShell`'s `modal-backdrop`, or Escape.
- **The modal is a container, not a presentational child.** It injects `RecurringRulesApi` itself and owns the list, the form, deletion and the scope question; `Account` only renders `<app-recurring-rules-modal>` behind a `rulesOpen` signal. Component tests mock `RecurringRulesApi` at that seam, so **e2e is the first place the real commands are exercised from the UI**.
- **The list reloads from `list_recurring_rules` after every successful write** rather than patching in place, so an e2e assertion on a row can follow a save without an extra reopen.
- **Rule row wording:** `<schedule summary> · <date range>`, e.g. `Tous les mois · depuis le 05/01/2026` and `Tous les ans · du 01/03/2026 au 01/03/2029`. Summaries are `Toutes les semaines` / `Toutes les N semaines` / `Tous les mois` / `Tous les N mois` / `Tous les ans` / `Tous les N ans`. Empty state: `Aucune écriture périodique sur ce compte.` The frequency select's options read `Hebdomadaire` / `Mensuelle` / `Annuelle`.
- **The scope dialog opens only when a template field actually differs from the stored rule** — label, poste, amount or description — compared against the rule, not tracked as the user types, so typing a change and undoing it by hand correctly asks nothing. Schedule-only edits go straight through as `ALL_FUTURE`. **Saving an edit without touching anything still calls `update_recurring_rule` (as `ALL_FUTURE`)**; it is not short-circuited to a no-op.
- **The schedule dates are native `<input type="date">`**, matching `AccountSettingsModal`'s "Date d'ouverture" rather than the register's `hlm-date-picker`. They render in the browser's locale and ignore the app's `DateFormat` setting; only the list rows honour it. WebdriverIO should set them by `YYYY-MM-DD` value, not by the displayed text.
- **The poste and frequency `<select>`s bind `[selected]` on their options, not `[value]` on the select.** A `<select>`'s value property only takes once its options exist, and `@for` fills them after the binding runs — binding `[value]` silently reverted both fields to their first option. Don't "simplify" it back.
- **The interval field is `type="text" inputmode="numeric"`, deliberately.** `type="number"` reads non-numeric text back as `""`, which makes "interval below 1" unreportable; as text, `deux` and `1,5` both raise the inline `Intervalle invalide : 1 au minimum`.
- **`LABEL_REQUIRED_MESSAGE` / `AMOUNT_INVALID_MESSAGE` now live in `src/app/features/account/entry-field-messages.ts`**, shared by `EntryForm` and the rules form so the two screens can't drift apart on user story 27. The validation rules themselves stay inline in each schema.
- **The toolbar button is styled like "Nouvelle écriture"** (filled, account colour, `data-accent-solid`), per the spec's "styled the same way". Two filled accent buttons now sit side by side in that toolbar — flagged in case a human wants the second one demoted to the bordered style the other toolbar controls use.
- **`InMemoryRecurringRulesApi` now stores rules and seeds two on account 1** ("Loyer" monthly, "Assurance habitation" yearly), so `npm run start:mock` opens onto a populated list. It accepts `scope` and ignores it — it generates no entries, so there is nothing for an override to apply to.
