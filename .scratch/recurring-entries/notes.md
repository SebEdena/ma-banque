# Recurring entries — cross-issue notes

## Cross-issue notes

_From issue 01 (recurring-rule-backend):_

- **The occurrence write lives on `RecurringRuleRepository`, not `EntryRepository`.** The spec's "`EntryDetails` gaining `recurring_rule_id`" was not done; `EntryDetails` is untouched and no existing call site changed. Instead `RecurringRuleRepository::insert_occurrence_if_absent(rule_id, account_id, date, template) -> Result<bool, RecurringError>` writes the entry directly, because the write is insert-if-absent against the partial unique index and that is a recurring-rule concern. **Issue 02's generator should call this, not `EntryRepository::create`.** `Ok(false)` means "already generated"; the return value is what a generated-count should be summed from.
- **The insert swallows exactly one conflict.** `is_duplicate_occurrence` matches a UNIQUE violation naming `entries.recurring_rule_id` + `entries.date`; every other failure surfaces as a `RecurringError`. Do not "simplify" this back to `INSERT OR IGNORE` — that would report a genuine write failure as "already generated" and silently drop an entry the user is owed.
- **Repository methods already built for generation, currently unused** and carrying `#[allow(dead_code)]` on the trait: `list_overrides`, `delete_override`, `insert_occurrence_if_absent`. Also `domain::recurring::occurrences_between` and `infra::clock::today()`. **Issue 02 should delete those three `#[allow(dead_code)]` attributes** (on the trait in `domain/recurring.rs`, on `occurrences_between`, and on `clock::today`) once it wires them up.
- **Override consumption is not implemented** — only its storage is. Issue 02 owns: applying an override's template to its occurrence, deleting it in the same transaction, and pruning overrides whose `occurrence_date` has passed unconsumed.
- **`last_viewed_date` is still never written.** Issue 01 touched no account code; the window bookkeeping is entirely issue 02's.
- **Naming on the wire** (issue 03's `RecurringRulesApi` must match): commands are `list_recurring_rules` / `create_recurring_rule` / `update_recurring_rule` / `delete_recurring_rule`. The rule payload is *flat* — `{ label, category_id, amount, description, frequency, interval, start_date, end_date }` — not split into template/schedule objects the way the Rust domain is. `amount` is a signed major-unit number (negative = débit), dates are `YYYY-MM-DD` strings, `end_date` is nullable.
- **`frequency` and `scope` cross the wire as raw strings**, parsed in Rust so a bad value returns a `RecurringError` rather than a deserialization failure. Accepted values: `WEEKLY` / `MONTHLY` / `YEARLY`, and `ALL_FUTURE` / `NEXT_OCCURRENCE_ONLY`. `update_recurring_rule` takes `scope` as a third argument alongside `id` and `input`.
- **The backend decides when scope matters, so the UI's dialog is advisory.** `update_rule` compares the submitted schedule against the stored one; if it differs, the edit is forced to `AllFuture` and the rule's outstanding overrides are discarded, *whatever* scope was passed. Issue 03 still needs to skip the dialog for schedule-only edits (user story 21), but sending the "wrong" scope cannot corrupt anything.
- **`RecurringError` kinds issue 03's `parseRecurringError` must cover:** `NotFound`, `EmptyLabel`, `InvalidInterval`, `EndDateBeforeStartDate`, `UnknownCategory`, `InvalidAmount`, `InvalidStoredValue`, `Io`. Serialized as `{ kind, message }` like `EntryError`.
- **Known non-atomicity, deliberately left:** a schedule change does `update` then `delete_overrides` as two repository calls with no transaction (the two-repositories-one-connection constraint means a use case can't hold one). A crash between them leaves a stale override, which issue 02's "prune overrides whose date has passed" makes self-healing.
- **`IsoDate` gained `add_weeks` / `add_months` / `add_years`**, all infallible and clamping day-of-month via the existing `days_in_month`. `chrono` was added but is used *only* by `infra::clock::today()`; date arithmetic is deliberately hand-rolled on `IsoDate` so `domain` stays dependency-free. Don't reach for `chrono` elsewhere.
