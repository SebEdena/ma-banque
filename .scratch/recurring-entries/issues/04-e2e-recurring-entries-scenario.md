**Bug fixed beyond the e2e scope (approved before implementing).** The first acceptance criterion was unreachable against the shipped code, for two independent reasons, so this ticket carries a `src-tauri` and an `account.ts` diff as well as the test:

1. **Backfill never happened for any account reachable through the UI.** `generate_due_for_account` opened every rule's window at the account's `last_viewed_date`, falling back to the rule's `start_date` only when that stamp was `NULL`. But the rules modal hangs off the account screen, and merely opening that screen calls `open_account`, which stamps `last_viewed_date = today` — so the stamp always existed by the time a rule could be created, every later open computed a window of `[today, today]`, and user story 6 ("a start date in the past … generated immediately") was dead in the shipped app. Fixed by anchoring a rule that has generated nothing yet at its own `start_date`, whatever the account stamp says; rules that have already generated keep the cheap `last_viewed_date` window, so the spec's idempotency design stays intact. Covered by `a_never_generated_rule_backfills_from_its_start_date_on_a_stamped_account`; the pre-existing `generation_covers_the_window_from_the_last_viewed_date_to_today` was re-seeded with a prior occurrence so it still exercises the stamp window.
2. **Closing the rules modal triggered nothing** — `(closed)` only cleared `rulesOpen`, and `Account` caches `open_account` per account id for its lifetime, so entries a new rule was owed appeared only after navigating away and back. `onRulesClosed()` now drops that cached promise and re-runs generation plus a register reload.

Known, spec-sanctioned consequence of fix 1: "has this rule generated?" is derived from the rule's live entries, so a user who deletes _every_ entry a rule produced makes it read as never-generated, and the whole run is re-created on the next open. The spec already allows this — Out of Scope says deleting a generated entry "does not prevent the same occurrence being generated again should the window ever cover it a second time".

Two WebdriverIO notes for whoever writes the next e2e spec, both learned the hard way here:

- **Assert row contents by XPath predicate, never by reading text back.** WebDriver's `getText` returns _rendered_ text, which comes back `""` under WebKitWebDriver for plenty of laid-out nodes — that is what fails the two pre-existing `entries.e2e.ts` scenarios, and it failed three assertions here until they were rewritten as `contains(., "…")` predicates asserted with `toExist`. `e2e/support/recurring-rules.ts`'s `ruleRowPartContaining` is the reusable shape.
- **Escape has to be delivered to a node inside the modal panel.** `ModalShell` listens for it on its backdrop, and a save that re-renders the list leaves focus on `<body>`, where the event never reaches that handler; clicking the backdrop doesn't work either, because WebDriver clicks an element's centre, which is the panel. `dismissRulesModal()` focuses an in-panel button first.
