# 01 — Recurring rule backend

**What to build:** The `RecurringRule` entity end to end at the backend boundary — schema, the pure scheduling calculation, the repository, and full CRUD (including the "next occurrence only" vs. "all future" edit scope) exposed as Tauri commands. No generation, no frontend UI yet: this ticket is done when a rule can be created, listed, edited (either scope), and deleted purely through the command layer.

**Blocked by:** None — can start immediately.

**Status:** done

- [x] Migration `migrations/0007_create_recurring_rules.sql` adds `recurring_rules` (account_id FK cascade, entry-shaped template columns mirroring `entries`' names/types/CHECKs, frequency/interval/start_date/end_date) and `recurring_rule_overrides` (rule_id FK cascade, occurrence_date, the same five template columns, `UNIQUE (rule_id, occurrence_date)`), plus the partial unique index `entries_one_occurrence_per_rule_date` on `entries (recurring_rule_id, date) WHERE recurring_rule_id IS NOT NULL`. `entries.recurring_rule_id` gains no `REFERENCES` clause (documented reasoning: SQLite can't retrofit an FK onto an existing money table).
- [x] `chrono` added as a dependency; `infra::clock::today() -> IsoDate` is the single function in the crate that reads the system clock.
- [x] `domain::recurring` module: `Frequency` (Weekly/Monthly/Yearly, `SCREAMING_SNAKE_CASE` serialization), `RuleTemplate` (amount as `SignedCents`), `RuleSchedule`, `RecurringRule`, `RecurringRuleDetails`, `OccurrenceOverride`, `RecurringError` (`thiserror` + `Serialize`, covering NotFound/EmptyLabel/InvalidInterval/EndDateBeforeStartDate/UnknownCategory/InvalidAmount/InvalidStoredValue/Io).
- [x] `occurrences_between(schedule, from, to) -> Vec<IsoDate>` is a pure free function, no repository/clock, returning every occurrence date in an inclusive window, clipped by start/end date.
- [x] Occurrence dates are **anchored, not chained**: the n-th occurrence is `start_date` advanced by `n × interval` periods from `start_date` itself (e.g. 2026-01-31 → 2026-02-28 → 2026-03-31 → 2026-04-30), not chained from the previous occurrence.
- [x] `IsoDate` gains `add_weeks`, `add_months`, `add_years`, infallible, clamping day-of-month to the target month's length via the existing `days_in_month` helper.
- [x] `RecurringRuleRepository` trait + `SqliteRecurringRuleRepository`: rule CRUD, override save/replace/consume, and an insert-if-absent occurrence-write path (used later by generation but implemented here alongside the repository).
- [x] `usecases::recurring::list_rules`/`create_rule`/`update_rule`/`delete_rule`: label non-blank, `interval >= 1`, `end_date >= start_date` when present, amount validated via `money::to_cents` exactly as `usecases::entry` does; category existence relies on the FK and surfaces as `UnknownCategory`.
- [x] `update_rule` accepts a scope: `AllFuture` mutates the rule row, leaving generated entries untouched; `NextOccurrenceOnly` leaves the rule row untouched and writes/replaces an override keyed to the rule's next due occurrence, consumed by generation when reached. Scope is only meaningful for template-field changes — schedule-field changes are always `AllFuture` and discard the rule's outstanding overrides.
- [x] `delete_rule` leaves previously-generated entries in place (no cascade onto `entries`).
- [x] `commands::recurring` exposes `list_recurring_rules`/`create_recurring_rule`/`update_recurring_rule`/`delete_recurring_rule`, mirroring `commands::entry`'s wire-boundary conversions (amount as major-unit `f64`, dates as `YYYY-MM-DD`).
- [x] Domain unit tests for `IsoDate` arithmetic: month/year boundary crossings, leap-year clamping (29 Feb → 28 Feb), mid-month day preserved unchanged.
- [x] Domain unit tests for `occurrences_between`: weekly/monthly/yearly with `interval = 1` and `> 1`; windows fully before/after the rule's range (empty); inclusive boundary cases at both ends; a single-day window; `end_date = None` running to the window's edge; the anchored 4-element month-end sequence asserted as one sequence.
- [x] Use-case tests for rule CRUD against a hand-written in-memory fake `RecurringRuleRepository` (no `mockall`): empty/whitespace label rejected; `interval = 0` rejected; `end_date < start_date` rejected, `end_date == start_date` accepted; invalid amount rejected; `AllFuture` update mutates the rule and leaves generated entries untouched; `NextOccurrenceOnly` writes an override on the correct next-due date (both for a rule with and without prior generated occurrences) and leaves the rule row untouched; a schedule-field change discards outstanding overrides; `delete_rule` leaves generated entries in place.
- [x] SQLite integration tests against a fresh `:memory:` database with all migrations applied: rule CRUD round-trips including `None` end_date/category_id; deleting an account cascades its rules; an unknown `category_id` surfaces `UnknownCategory`; override insert/replace respects the unique constraint; deleting a rule cascades its overrides and nulls `recurring_rule_id` on entries it generated while leaving those entries present; the occurrence insert path is insert-if-absent (a second insert for the same `(recurring_rule_id, date)` reports "already present" rather than erroring or duplicating).
- [x] Migration test: `0007` applies cleanly to a database with pre-existing accounts/entries.
